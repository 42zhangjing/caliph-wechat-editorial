# 群聊编辑工作流 v2

## 一、素材范围

source JSON 来自 yichen `digest-source`，只代表已经存在于本地 vault 的消息。开始前确认：群名、起止日期、素材最后一条消息时间、图片/视频/语音是否可读。

没有最新素材时明确说明缺口，不用旧数据冒充最新数据。

`prepare_source.py` 只保留编辑需要的字段，并给每条消息增加 `M000001` 形式的安全 anchor。anchor 用于审稿定位，不暴露微信内部 ID。

## 二、Round 1：全量扫描与 Story Map

先读完整批次，再决定什么值得写。

内部 Story Map 推荐格式：

```text
01 09:20—10:05 / AI 工具
参与：A、B、C
发生：……
转折：……
锚点：M000032 A「原话片段」；M000041 B「原话片段」
媒体依赖：无 / 图片不可见 / 已有描述
候选价值：major / minor
```

扫描原则：

- 话题切换优先看内容跳转、参与者变化、明显时间间隔。
- 多人连续讨论合并成一个故事，保留“谁推动了哪一步”。
- 相邻消息不能因为时间接近就自动归给同一人。
- 纯表情、单独“哈哈哈/收到/好的”、重复转发通常过滤；它们若触发后续讨论则保留为上下文。
- 图片或视频成为讨论核心时做 `媒体依赖` 标记；看不到媒体时不补写画面。
- 先宽后窄：日报可先列 5—10 个候选，再收敛到 3—6 个；周报可先按每天列，再收敛到 4—7 个跨日故事。

## 三、日报编排

日报强调现场、节奏与当天转折。

建议内容层级：

```text
报头
→ Lead
→ 3—6 个故事节点
→ 本期角色
→ 关键数字
→ 留下的问题
```

Lead 只出现在第 1 版。后续版使用紧凑报头和 continuation strip。

日报故事优先级通常是：

1. 最有连续讨论链、最能代表当天现场的主线；
2. 明显改变讨论方向的节点；
3. 有真实产出、查证、决策或解决方案的节点；
4. 有辨识度且能缓冲/改变群体节奏的生活、玩笑或消费节点。

不机械按上午/下午/晚上切段。

## 四、周报编排

周报寻找变化和跨日关系。

重点找：

- 一周内反复出现的主题；
- 某个观点如何变化；
- 玩笑怎样变成认真问题；
- 技术、政策、产品或生活话题怎样彼此连接；
- 群友承担的提问、查证、解释、反驳、产出、缓冲等角色；
- 本周仍未闭合的问题。

周报首页更接近 feature opener，Lead 可以更宽松；正文不要按“周一发生什么、周二发生什么”流水排列。

## 五、Round 2：写作顺序

先写 sections，再写 Lead。

每个 section 至少包含：

- 一个具体标题；
- 时间/主题 eyebrow；
- 发生了什么；
- 谁推动；
- 转折或结果；
- 必要的短引用；
- `evidence` 证据等级；
- `priority` 排版优先级。

写完全部 sections 后，再用成稿反推 Lead 的 title / dek / body / tags。

## 六、CALIPH Editorial Voice

### 普通版

语气：冷静、具体、自然、克制。

- 多用动作和事实，少用抽象判断。
- 保留人物说话的辨识度，引用要短。
- 不把一次发言上升为稳定人格。
- 不使用“今天群里热闹非凡”“围绕某主题展开讨论”这类空标题。
- 避免连续对仗、四字短语堆叠和过度总结。
- 编辑文字默认不使用 `不是……而是……`、`并非……而是……`。
- 减少“真正值得关注的是”“某种意义上”“归根结底”“值得注意的是”“这背后反映了”等通用 AI 句式。

### 毒舌版

毒舌版从已经审计的普通版 Story Map 出发重写。统计、故事顺序、证据等级、逐字引用和未决问题不能变；变化的是观察角度、标题张力与点评密度。

先写一版“敢说”的内部草稿：找出每个故事里最荒诞的因果链、最明显的反差、反复横跳、夸张愿望或现场转折。完成后单独做红线审校，而不是一边写一边把所有槽点磨平。

每个故事至少完成其中一项，再决定是否值得进入 roast 版：

- 把公开观点里的漏洞、跳跃或过度自信讲具体；
- 把一次公开行为与它后续的反转并置；
- 把群聊的集体跑题、抢答、补刀或过度认真写成现场喜剧；
- 用本期已出现的词、梗或前后呼应形成 callback，但不依赖读者知道群外历史。

写作落点：

| 部位 | roast 的写法 |
| --- | --- |
| 报头 / Lead | 标题带 `毒舌版`；开场直接点当天最荒诞的转折，不用泛泛的“今天很热闹”。 |
| 故事标题 | 可以更损、更短、更像报纸标题，但标题仍须准确描述真实讨论。 |
| 正文 | 先交代发生了什么，再给评论；每段至少保留一个可回查的具体动作、观点或转折。 |
| 引用 | `quotes[].text` 逐字保留；必要时用 `quotes[].comment` 加 1 句短点评，明确是编辑点评。 |
| 人物卡 | 使用 `roast_note` 写本期反差、惯性或槽点；renderer 会显示「不留情面版」。 |
| 页脚 | 默认使用“本简报由一个没有感情的 AI 自动生成，如有冒犯，概不负责。” |

好的点评针对“本期发生的事”，而不是给人贴永久标签。例如：

- 可以写：“三句话把购车预算从劳斯莱斯校准到宾利，宏观愿景终于有了落地价。”
- 不写：“这人就是虚荣又不懂经济。”

- 可以写：“刚说不想入坑，下一分钟已经在讨论两万级耳机，消费主义的门禁形同虚设。”
- 不写：“这种人注定会破产。”

安全红线：

- 不攻击外貌、身材、体重、年龄、健康、疾病、家庭或私人关系；
- 不用医学或心理诊断制造笑点，不写“该看医生”“典型 ADHD”等；
- 不根据时间戳推断作息、时区或线下状态；
- 不揣测性取向、宗教、政治立场或其它未公开身份属性；
- 可以批评观点荒谬、论证跳步、公开行为反复，不贬低对方的发言权或人格价值；
- 本期没有明确槽点的人给温和调侃或不入选人物卡，绝不硬凑。

目标是“读到会笑，也能复盘当天/本周发生了什么”。

## 七、引用与事实

原话只能来自当前 `source-normalized.json`。

- `quotes[].text` 必须逐字存在。
- speaker 必须匹配。
- 时间用于辅助缩小候选范围。
- 找不到原话就改成间接引语或删除。

对链接和文件只陈述消息中明确可见的信息。没有外部核验时，链接标题、转述、政策材料、榜单截图等使用 `linked_claim` 或在正文保留“群内转发/转述”的限定。

标题、dek 与 closing 同样受事实约束，不能靠页脚免责声明替代谨慎措辞。

## 八、Evidence 使用

- `direct_quote`：故事核心由一条或多条可定位原话直接支撑。
- `group_observation`：对聊天过程本身的编辑归纳。
- `linked_claim`：外链、截图、文件标题、群内转述等未外部核验材料。
- `externally_verified`：本次明确完成外部查证。
- `editorial_inference`：对讨论结构、变化或关系的编辑推断。

一个 section 只填主要 evidence，正文里继续区分不同材料。

## 九、人物卡

人物卡写本期角色与贡献。roast 模式优先显示 `roast_note`，把本期可见反差和槽点写成一句短评；它不是长期人格档案。

推荐 4—8 人；人数少时自然减少。

好的 role：

```text
资料投放 / 现实验算
硬件经验 / 问题收束
追问 / 查证
气氛缓冲 / 群规戏仿
```

避免：

```text
典型焦虑人格
永远唱反调的人
群里最聪明的人
```

发言数可以显示，但降低视觉权重。人物入选由故事贡献决定。

## 十、视觉编排

### 普通版

- 现代 newspaper / independent magazine 气质；
- 12 栏基础网格；
- serif 长正文、sans 标题、mono 数据与栏目标签；
- 米白纸张、墨黑、克制朱砂红、深蓝辅助；
- 更宽松留白和更强层级；
- 页面节奏优先于模板填满。

### 毒舌版

- 沿用品牌骨架；
- 高亮黄 / 黑 / 红信号更强；
- pull quote 可以反白；
- 标题比例更激进；
- 正文仍保持长时间阅读能力。

### 日报 vs 周报

日报首页接近 front page；周报首页接近 feature opener。

第 2 页以后不重复完整 Lead。故事编号跨页连续。

## 十一、头像

头像默认开启。

- 群头像：每期尝试导出。
- 人物头像：所有入选人物尝试导出。
- 缺头像：首字占位。
- 用户明确要求无头像：关闭。
- 同名对应多个内部账号：视为歧义，不猜；用占位并提示。

## 十二、Round 3：机器 + 人工审稿

先运行：

```bash
python scripts/validate_report.py report.json --source source-normalized.json
```

必须检查：

1. 每个引用逐字存在且 speaker 正确；
2. `kind/style/tone/evidence/priority` 合法；
3. sections 和 stats 数量合理；
4. manual pages 没有越界或重复 section；
5. 编辑文字未使用禁用对比句式；
6. Lead 和标题没有把未核验材料写成外部既定事实；
7. 周报确实体现跨日变化；
8. 普通版和毒舌版共用事实骨架。

validator 通过后再 render。

## 十三、自动分页

默认 `layout.page_mode = auto`。

模型负责：

- section 顺序；
- `major/minor`；
- 哪些内容值得留。

renderer 负责：

- 先按双栏卡片而不是单条累计估算 story weight；
- 用 Chrome 实测每个候选页，优先把能同时容纳的 story card 放到同一张 A3；
- 最后一页加入人物、stats、closing 后再实测，空间不足时把最后一条 story 移到该页；
- 自动分配物理 A3 页；
- 第一版保留完整 Lead；
- 后续版 compact header；
- 最后一版默认放人物、数据、closing。

页面主体会撑到页脚上方；当一页有多行 story card 时，行间会使用可用高度做纵向分配；最后一行只有一张卡时，该卡跨双栏收束。不要为了填纸补虚构内容，也不要让页脚停在内容中段、下方留下像漏排一样的大块空白。

特殊封面或专题版才使用 manual pages。

## 十四、Layout Preflight

渲染器用 Chrome 实际检查 A3 页面。它等待 `DOMContentLoaded`、可用字体与两帧 layout 稳定，不等待 `window.load`；preflight 副本会把远程图片替换为同尺寸占位图，因此 CALIPH Logo 或其它网络资源的慢响应不会阻塞版面检测。正式 HTML / PNG / PDF 保留原本的品牌资源。

检查条件：

```text
scrollHeight <= clientHeight
```

出现 overflow 时渲染失败。必须调整文字或分页后重新导出。自动分页的目标是避免无意义的单 story 空页，不是用虚构内容填满纸张；保留合理留白，但页面不应因为保守估算而连续只放一张半栏卡片。

这个检查用于防止固定高度 + `overflow:hidden` 静默裁掉最后几行。

## 十五、输出

默认根目录：

```text
/Users/chengyu/Downloads/微信群报/<群名>/
```

默认格式：PNG + PDF。

用户要求时额外保留 HTML。HTML 图片复制到同名 `_assets/` 目录，页面只使用相对 URL，不暴露本机绝对路径。

命名：

```text
<群名>_日报_<日期>_普通版.pdf
<群名>_日报_<日期>_普通版_p01.png
<群名>_周报_<开始>--<结束>_毒舌版.pdf
```
